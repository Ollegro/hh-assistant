# Журнал разработки hh-assistant

Формат записи: **дата — что сделано → решение и почему → проблема и как решена → следующий шаг.**

## 21.10.2026 — разбор возможностей hh.ru и выбор схемы

**Сделано:** изучена спецификация API hh.ru, выполнены живые проверки эндпоинтов
(`tools/hh_api_check.py`, `tools/hh_spec_dump.py`, `tools/hh_api_probe403.py`),
собран документ `01_Разбор_API_hh.md` и предложение `02_Предложение_автоотклики.md`.

**Решение:** поиск вакансий анонимно через API закрыт (403), отклик через API
недоступен (закрыт 15.12.2025). Выбран **вариант A — «полуавтомат»**: приложение
готовит очередь и письма, отправку делает человек. Почему: нулевой риск блокировки
аккаунта и отсутствие серой зоны (автоматизация интерфейса — против правил hh).

**Проблема:** «100 откликов в сутки через API» технически невозможно.
**Как решено:** цель переформулирована — не количество откликов, а точность подбора
и готовое персональное письмо.

**Следующий шаг:** MVP на стандартной библиотеке Python без зависимостей.

## 22.10.2026 — MVP: сбор, скоринг, письма, очередь, веб-UI

**Сделано:**
- `hhassist/collector.py` — HTML-адаптер hh.ru: поиск по запросам (`search_ids`) и
  разбор карточки (`parse_vacancy`: заголовок, компания, зарплата, формат, опыт, стек,
  описание), корректный `User-Agent`, повторы при 403/429, gzip.
- `hhassist/storage.py` — SQLite: `vacancies`, `scores`, `letters`, `applications`, `events`.
- `hhassist/scoring.py` — правила 0–100 + опциональная LLM-оценка (0.45 × правила + 0.55 × LLM).
- `hhassist/letters.py` — письмо: LLM few-shot по готовым образцам или офлайн-сборка
  из проверенных фактов профиля + `validate_letter` (длина, отсутствие Markdown, приветствие).
- `hhassist/queue.py` — очередь, дедупликация (одна вакансия — один отклик), дневной лимит, экспорт `.txt`.
- `hhassist/web.py` — локальный веб-UI: таблица вакансий, карточка с письмом и кнопками.
- `cli.py` — команды `collect`, `score`, `letters`, `serve`, `export`, `list`, `stats`, `reset`.
- `tools/run_hh_assistant.py` — ASCII-обёртка запуска (кириллица в пути ломает консоль Windows).

**Решение:** никаких внешних зависимостей — только stdlib, чтобы приложение
запускалось одним `python` и легко переносилось.

**Проблема:** первый прогон парсера давал пустые поля.
**Как решено:** разметка hh отдаёт данные в JSON внутри страницы, поэтому поля берутся
не только из `data-qa`-атрибутов, но и из `workFormats`, `workExperience`, `keySkills`
(проверено на сохранённых HTML-страницах).

**Результат проверки:** 4 вакансии с hh.ru, оценки 53–83, 2 письма ~1,4 тыс. знаков.

**Следующий шаг:** убрать консоль из основного сценария — кнопки в веб-интерфейсе.

## 23.10.2026 — кнопки в веб-UI, переименование папки, учёт резюме, тесты

**Сделано:**
1. Кнопки в веб-интерфейсе: `POST /run/collect`, `/run/score`, `/run/letters` и ссылка
   `/export`; отчёт о действии возвращается на главную через `?msg=…`.
2. `Запустить hh-assistant.bat` — запуск сервера в свёрнутом окне и открытие браузера.
3. `tools/check_hh_server.py` — автоматическая проверка сервера и кнопок (без ручных кликов).
4. Дневной лимит поднят со 100 до **200** (максимум hh.ru) — в `Settings`, `.env`-fallback и документации.
5. Поиск и скоринг теперь учитывают **резюме кандидата**: расширен `config/profile.json`
   (целевые роли, уровень, история работы, стек must/nice/avoid, образование, языки, стоп-лист компаний),
   добавлен модуль `hhassist/matching.py` и выжимка резюме для LLM-промптов.
6. Тесты на stdlib: `tests/` (парсер на фикстуре, matching, scoring, письма) — **34 теста, OK**.

**Проблема 1: переименование папки сломало запуск.**
Папка проекта переименована в `работа с hh.ru`, приложение — в `APPLICATION-hh-assistant`,
а `tools/run_hh_assistant.py` и `tools/check_hh_server.py` искали жёсткий путь `hh-assistant`.
**Как решено:** добавлен `tools/hh_app_path.py` — поиск папки с `cli.py` по списку
кандидатов и сканированием каталога; оба скрипта используют его. Теперь папку можно
переименовывать и переносить.

**Проблема 2: few-shot образцы писем молча не находились.**
`letters.SAMPLES_GLOB` поднимался ровно на три уровня и указывал в `Работа с hh.ru по API\Отклики на вакансии`,
тогда как письма лежат в корне проекта. Генерация не падала — просто теряла 3 образца стиля.
**Как решено:** `_find_samples_glob()` поднимается вверх по дереву (до 6 уровней) и берёт
первый найденный каталог `Отклики на вакансии`. Проверка: `python tools/check_samples.py` → 3 образца.

**Проблема 3: стоп-лист компаний не обнулял балл.**
Тест `test_excluded_company_is_hard_stop` показал 24 вместо 0: проверка стояла до начислений
за зарплату и формат. **Как решено:** проверка перенесена в конец расчёта, после неё балл = 0
и вердикт «не откликаться».

**Проблема 4 (диагностика):** терминал агента не запускался, так как рабочий каталог VS Code
указывал на переименованную папку. **Как решено:** папка проекта переоткрыта в VS Code.

**Результат проверок:**
- `stats`: 15 вакансий, 4 оценки, 2 письма, лимит 200;
- веб: `/` 200, `/export` 200, `POST /run/score` 303 («оценено вакансий: 15»),
  `POST /run/letters` 303 («создано писем: 7»), карточка `/v/{id}` 200 с textarea и блоком
  «Сопоставление с профилем»;
- скоринг после учёта резюме: 13…100 (было 53–89 в узком кластере) — целевые
  «Промпт-инженер» получили 100, непрофильные роли 13–48;
- тесты: 34 из 34.

**Следующий шаг:** подключить LLM-ключ для скоринга и персонализации писем; затем —
воронка ответов и решение о публикации репозитория.

## 23.10.2026 (этап 4) — LLM-контур: единый клиент, повторы, отказоустойчивость

**Сделано:**
1. `hhassist/llm.py` — единый клиент OpenAI-совместимого API: `is_enabled`, `resolve_base_url`,
   `describe`, `chat`, `chat_json`, `extract_json`, `LLMError`.
2. Адрес API подставляется по `LLM_PROVIDER` (openai, openrouter, deepseek, ollama, yandex),
   поэтому `LLM_BASE_URL` нужен только для своего или корпоративного шлюза.
3. Повторы при временных сбоях (429/5xx, таймауты, обрыв сети) с нарастающей паузой; ошибки ключа
   и адреса сообщаются сразу и с подсказкой: «LLM отклонил ключ (HTTP 401): проверьте LLM_API_KEY».
4. Ключ API не попадает ни в сообщения об ошибках, ни в вывод приложения: в UI и консоли видно
   только «задан / не задан».
5. `scoring.py` и `letters.py` переведены на общий клиент — дублирование HTTP-кода убрано.
   При сбое LLM скоринг откатывается к правилам и добавляет причину «LLM недоступен: …»,
   письмо — к офлайн-сборке (`model = offline`); приложение не падает.
6. Новые настройки `.env`: `LLM_TIMEOUT`, `LLM_RETRIES`, `LLM_JSON_MODE`.
7. `tools/check_llm.py` — диагностика в четыре шага: настройки → связь с моделью → скоринг
   тестовой вакансии → письмо; при отсутствии ключа печатает, что вписать в `.env`.
8. Режим LLM виден в шапке веб-интерфейса и в `stats`.
9. Тесты `tests/test_llm.py` (без сети, через подмену `urlopen`): провайдеры, «ключ не утекает»,
   повтор после 429, JSON-режим, откат к правилам, формула 0.45/0.55, чтение настроек из `.env`.

**Проблема 1: HTTP-код был скопирован в двух модулях.**
`scoring.py` и `letters.py` сами собирали запрос, таймауты различались (90 и 120 с), а ошибки
глушились `except Exception`. **Как решено:** общий клиент `llm.py`, единые таймаут и повторы.

**Проблема 2: при сбое LLM причина терялась.**
Оценка молча откатывалась к правилам, и понять, что модель недоступна, было нельзя.
**Как решено:** причина «LLM недоступен: <ошибка>» добавляется к причинам балла.

**Проблема 3 (нашла тестовая диагностика): утечка файловых дескрипторов.**
`letters.load_samples` и `config.load_env` читали файлы без `with`, Python сыпал
`ResourceWarning: unclosed file`. **Как решено:** оба места переведены на контекстный менеджер.

**Результат проверок:**
- тесты: **57 из 57 OK** (было 34; +23 на LLM-контур);
- `python tools/check_llm.py` без ключа: печатает «LLM не настроен (нет LLM_API_KEY, нет
  LLM_MODEL, нет LLM_BASE_URL или LLM_PROVIDER) — офлайн-режим» и инструкцию для `.env`;
- `stats`: LLM не настроен (офлайн-режим), 15 вакансий, 15 оценок, 9 писем, лимит 200.

**Следующий шаг:** вписать ключ в `.env`, прогнать `check_llm.py`, сравнить скоринг
офлайн и с LLM на реальных вакансиях и при необходимости откалибровать вес 0.45/0.55.

## 23.10.2026 — API-источник hh.ru с откатом на HTML, `api-check`, 22 новых теста

**Сделано:**
- `hhassist/hh_api.py` — клиент api.hh.ru: токен приложения (`POST /token`,
  `client_credentials`, тело form-urlencoded), приоритет готового `HH_APP_TOKEN`,
  Bearer-заголовок, gzip, ETag/`304`, повторы на `429/5xx` с учётом `Retry-After`
  (на `401/403` повторов нет), `HHApiError(status, value, request_id)`; помощники
  `search_vacancies`, `get_vacancy`, `me`, `probe`, проверка глубины `page * per_page ≤ 2000`
  и `per_page ≤ 100` до запроса.
- `hhassist/api_adapter.py` — JSON API → та же модель вакансии, что у HTML-парсера
  (`name→title`, `employer.name→company`, `salary.*`, `work_format`/`schedule`,
  `experience.id`, `key_skills`, описание из `description` или `snippet`, `source="api"`).
- `collector.collect(query, area, pages, per_page, limit, source, details)` — единая точка
  входа: `auto` (API при наличии токена, иначе HTML), `api`, `html`; при ошибке API в `auto`
  откат на HTML, причина возвращается в `info` и пишется в `events` как `source_fallback`.
- `config.py` — `HH_SOURCE`, `HH_API_TIMEOUT`, `HH_API_RETRIES` и `Settings.has_app_token()`;
  `.env.example` дополнен этими полями и предупреждением про закрытие API для соискателей.
- `cli.py` — `collect --source auto|api|html --no-details` и новая команда `api-check`
  (токен → `/me` → `/vacancies`; при ошибке печатаются код, `value` и `request_id`).
- `tools/hh_api_token.py` — тот же отчёт в `out/hh-api-check.txt`; секреты не печатаются
  (только источник токена и его длина).
- Тесты: `tests/test_hh_api.py` + фикстуры `tests/fixtures/{search_api,vacancy_api}.json` —
  паритет адаптера с HTML-моделью, пагинация и лимит 2000, повтор на 429 с `Retry-After: 0`,
  403 (`forbidden` и `oauth/bad_authorization`), откат `auto`→HTML и запись события,
  `HH_SOURCE=api` без токена — понятная ошибка без сетевого вызова, отсутствие токена
  в текстах ошибок. Сеть подменяется через `hh_api._open`. Итого **83 теста**, OK.

**Решение:** API-путь реализован «на будущее», но основным источником остаётся HTML-парсер.
Почему: в форме заявки dev.hh.ru (проверено 23.10.2026) поле «Приложением будут пользоваться»
содержит только варианты для работодателей; отдельного варианта «соискатель» нет, рядом
примечание о прекращении поддержки API для соискателей с 15.12.2025. Токен приложения
для личного ассистента соискателя получить не по чему.

**Проблема:** без токена `api-check` падал бы трейсбеком.
**Как решено:** `HHApiError` с пустым `status` и понятным текстом «токен hh не настроен…»,
команда печатает «ошибка настройка hh» и подсказку `HH_SOURCE=html`, код возврата 1.

**Проблема:** `HH_USER_AGENT` в `.env` был равен значению из шаблона
(`hh-assistant/0.1 (user@example.com)`), а hh требует реальный контактный e-mail
и сверяет его с заявкой. **Как решено:** вернул реальный адрес (значение по умолчанию
из `config.py`).

**Уточнение по заявке (сценарий ИП / кадровое агентство, 23.10.2026):** проверены «Условия
использования сервиса API» (dev.hh.ru/admin/developer_agreement). п.1.2 прямо допускает учётную
запись «для работодателей, кадровых агентств и частных рекрутеров», п.1.5 разрешает таким
пользователям применять Сервис «только для целей привлечения потенциальных работников и их
последующего трудоустройства», п.1.6 даёт hh право отказать при иных целях, п.1.3 — отказать
без компенсации. Итог: заявка под ИП-агентство возможна и легальна, но токен от неё нельзя
использовать как личный ассистент соискателя; HTML-парсер остаётся основным путём для личного
поиска. Разбор с цитатами и чек-лист — `01_Разбор_API_hh.md` §7; предупреждение добавлено
в `.env.example`.

**Заявка в dev.hh.ru подготовлена, отправка отложена (23.10.2026):** тексты собраны в
`../04_Заявка_приложения_hh.md` (+ `.txt` для копирования): чек-лист предусловий, поля формы,
описание приложения, сопроводительное письмо, отдельное уточняющее письмо в поддержку API,
шаги после одобрения и список формулировок, которых в заявке быть не должно. Решение: остаёмся
на HTML-парсере (`HH_SOURCE=auto`/`html`), заявку подаём только при реальном агентском сценарии
(ИП + профиль «кадровое агентство»), иначе — сначала бесплатное уточнение в поддержку.
В `.env` выставлено явно `HH_SOURCE=html` (проверено: `get_settings().hh_source == "html"`,
`has_app_token() is False`), чтобы API-путь не включался случайно.

**Следующий шаг:** если заявка на dev.hh.ru всё же будет одобрена (или появится доступ
работодателя) — `HH_APP_TOKEN` в `.env`, `python cli.py api-check`, затем `HH_SOURCE=api`;
иначе — этапы 5–6 плана (воронка ответов, `export --csv`, демо-данные, CI).

## 23.10.2026 (вечер): сбор по всей выдаче, честные числа в отчёте

**Проблема:** кнопка «Собрать вакансии» брала только первые 3 запроса и по 5 вакансий
(числа были зашиты в `web.run_action`) — при пяти запросах в `config/queries.txt` часть
не использовалась, а «Оценить» каждый раз пересчитывала все вакансии заново, тратя время
и токены LLM.

**Как решено:**
- `config.py` — поля `Settings.collect_limit` (20), `collect_pages` (1),
  `collect_queries` (0 = все запросы) из `.env` (`COLLECT_LIMIT`, `COLLECT_PAGES`,
  `COLLECT_QUERIES`); `.env.example` дополнен блоком с примером «широкого» сбора.
- `web.run_action("collect")` — проходит по всем запросам из `config/queries.txt`
  (или первым `COLLECT_QUERIES`), на каждый запрос `pages=COLLECT_PAGES`,
  `limit=COLLECT_LIMIT`; ошибка одного запроса не прерывает остальные (попадает в отчёт
  и в `events` как `collect_error`), итог прогона пишется в `events` как `collect`.
  Отчёт: «собрано вакансий: N из M найденных (источник: …, запросов: …, лимит: …)».
- `collector.collect` — `info["found"]` теперь всегда «сколько нашёл поиск до лимита»,
  добавлено `info["taken"]` (сколько реально скачано) — одинаково для HTML- и API-пути;
  `cli collect` печатает оба числа.

## 23.10.2026 (ночь): чистка проекта, один код для CLI и веба, подготовка репозитория

**Проблема:** логика сбора, оценки и писем была продублирована в `cli.py` и `hhassist/web.py`
(два почти одинаковых цикла), каждый `upsert_vacancy`/`save_score` делал собственный коммит
SQLite, а `tests/` и `tools/` лежали в родительской папке — папку приложения нельзя было
опубликовать как самостоятельный репозиторий.

**Как решено:**
- новый модуль `hhassist/jobs.py`: `collect_queries`, `score_pending`, `make_letters`,
  `export_letters`; CLI и веб-интерфейс вызывают один и тот же код, тексты отчётов сохранены;
- `hhassist/storage.py` — параметр `commit=True` у `upsert_vacancy`, `save_score`,
  `save_letter`, `add_application`, `log_event`; пакетные действия пишут одной транзакцией
  на прогон (было: коммит на каждую вакансию/оценку/письмо);
- убраны неиспользуемые импорты (`json`, `scoring`, `queue` в `web.py`; `json`, `queue`,
  `scoring` в `cli.py`);
- структура: `tests/` и `tools/` перенесены внутрь папки приложения — `tests/_bootstrap.py`
  больше не ищет приложение через `tools/hh_app_path.py`, корень вычисляется от папки тестов;
  все три `.bat` работают из `%~dp0`;
- в `tools/` приложения: `run_hh_assistant.py`, `check_serve.py`, `check_hh_server.py`,
  `check_llm.py`, `compare_scores.py`, `check_samples.py`, `check_hh_parse.py`,
  `hh_api_token.py` (у всех путь к приложению вычисляется от файла, без внешних хелперов);
  удалён устаревший `check_hh_web.py` — он ссылался на старое имя папки `hh-assistant`;
- удалён мусор: `__pycache__`, дубли папки `out/` в корне, временные отчёты проверок.

**Тесты:** новый `tests/test_jobs.py` — 12 тестов (оценка только новых, `force=True`,
письма по порогу/лимиту и без повторов, ошибка одного запроса не рушит сбор,
`found`/`taken`, батч-коммит `commit=False` + один `commit`). Итого **108 тестов**, OK;
`compileall` — OK; `tools/check_serve.py` — GET `/` → 200, 5180 байт, четыре кнопки,
сервер останавливается; `tools/check_hh_server.py` — зелёный.

**Следующий шаг:** `git init` в папке приложения, первый коммит и публикация на GitHub;
затем этапы 5–6 плана (воронка ответов, `export --csv`).
