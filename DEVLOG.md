## 24.10.2026 — без порога и городов, окно правил оценки, читаемое описание, воронка удалена

**Сделано** по замечаниям заказчика: «логику порога убирай», «кнопку города убирай»,
«что делает Оценить вакансию?», «описание вакансии не форматировано — там код»,
«что за текст с баллом 90?», «должно быть всплывающее окно о правилах оценки»,
«/funnel — убирай полностью».

**Порог убран целиком.** Нет селекта «порог», `?threshold=`, отсечения по баллу
(`queue.next_batch`), порога для писем (`jobs.letter_vacancies`), `storage.score_counts`,
настройки `score_threshold` / `SCORE_THRESHOLD` и `letters --threshold`. В сводке главной
осталось «собрано · оценено · без оценки · в списке». Ориентир — балл и цветной бейдж
вердикта («откликаться» / «условно» / «не откликаться») в колонке «Оценка».

**Фильтр по городам убран.** Остался один селект — регион (субъект РФ); он же задаёт
регион сбора. `storage.area_counts` и параметр `area` в SQL удалены. Колонка «Город»
осталась и теперь действительно показывает город (раньше при заполненном субъекте РФ
в ней был субъект).

**Карточка вакансии.** Причины оценки больше не печатаются сырым JSON: `scores.reasons`
разбирается в список `<li>`, последний элемент «фокус: …» выносится в строку
«Что подчеркнуть в письме». Кнопка «Оценить вакансию» переименована в
«Переоценить вакансию» (она пересчитывает балл именно этой вакансии — правилами и LLM;
пакетная «Оценить» берёт только неоценённые). Появилось окно `<dialog id='rules'>`
«Как считается оценка»: таблица правил с весами, формула «45 % правила + 55 % LLM»,
цифры по вакансии (балл правил / балл LLM / итог / вердикт) и сработавшие причины.
Открывается кнопкой «Правила оценки» и автоматически после переоценки (`?rated=1`).

**Схема и расчёт.** В `scores` добавлены `rule_score` и `llm_score` (миграция через
существующий `MIGRATIONS`), `scoring.score_vacancy` возвращает составляющие, веса правил
вынесены в константы, а `scoring.RULE_WEIGHTS` — единый источник для окна правил
(надпись не разойдётся с расчётом). Старые оценки показывают «составляющие не сохранены».

**Описание вакансии.** Причина мусора: regex брал всё от `data-qa="vacancy-description"`
до конца документа, и в описание попадал код страницы (в локальной базе 10 записей из 147
содержали jQuery/swiper), а `clean()` схлопывал все пробелы — переносов не было ни у одной.
Теперь `collector.html_to_text` превращает `p/div/br/li` в переводы строк (`li` — «• »),
`description_of` ограничивает фрагмент закрытием блока по балансу `<div>` и режет по
маркерам JS; `api_adapter` тоже использует `html_to_text`. В карточке — `<div class='desc'>`
с `white-space:pre-line` и ссылка «полный текст на hh».
Новый `tools/refresh_descriptions.py` перекачивает карточки и обновляет только описание
(`--dry-run`, `--all`, `--limit`, `--pause`); локально перекачаны все 147 записей,
на сервере запущен тот же скрипт.

**Воронка удалена полностью.** Нет маршрута `/funnel`, `render_funnel`, `_breakdown_table`,
модуля `hhassist/analytics.py`, команды `cli.py funnel`, `queue.responded` и тестов воронки.
CSV-выгрузка переехала в `hhassist/csv_export.py` — `python cli.py export --csv` работает
как раньше.

**Проверено:** `Ran 246 tests … OK` (+11: окно правил и его данные, составляющие оценки,
форматирование описания, отбор для перекачки, отсутствие порога и города). Живой прогон
`_smoke.py` на временной базе — **31/31**: главная без порога/города/воронки, карточка со
списком причин и окном правил, переоценка (`?rated=1` → окно открыто), письмо для одной
вакансии, правка письма, статусы, mark/skip, экспорт, статика, 404 на `/funnel`, сбор,
сохранение запросов. На сервере: селектов порога и города нет, `/funnel` → 404, карточка
содержит окно правил, `POST /run/score/<id>` → 303, ошибок в журнале за 10 минут — 0.

**Следующий шаг:** заказчику нажать «Переоценить вакансию» — откроется окно с правилами и
результатом. Если в правилах что-то не так (веса, формулировки) — правится в одном месте:
`scoring.RULE_WEIGHTS` + константы рядом.

## 24.10.2026 — пустая страница при «Оценить», письмо для одной вакансии, без «Воронки»

**Сделано** по замечаниям заказчика: «нажал Оценить — чёрный экран», «Сгенерировать письма —
тоже чёрный экран», «почему нельзя сгенерировать письмо только на выбранную вакансию?»,
«Воронка — зачем она нужна?».

**Проблема и как решена.**

- В журнале сервера — `sqlite3.OperationalError: database is locked` в `run_action` и
  `make_letters`. Заказчик нажал кнопку восемь раз подряд (14:35:29–14:37:29): первый прогон
  оценки шёл с открытой транзакцией всё время запросов к LLM (минуты), остальные клики падали
  через 5 с (таймаут SQLite по умолчанию), а `ThreadingHTTPServer` при необработанном исключении
  просто закрывал соединение — браузер показывал «Пустая страница».
- `storage.connect()`: `PRAGMA journal_mode=WAL`, `busy_timeout` 30 с, `synchronous=NORMAL`
  (было: rollback journal и 5 с). Читатели больше не блокируют писателя, писатель ждёт очереди.
- `jobs`: промежуточный `commit` каждые 5 записей (`COMMIT_EVERY`) — блокировка записи не держится
  весь прогон.
- `web`: один прогон за раз (`RUN_LOCK`), второй клик получает «уже выполняется…» вместо падения.
- `web`: пакетные сбор/оценка/письма выполняются в фоновом потоке (`start_action`): страница
  отвечает сразу («запущено: оценка»), показывает «идёт оценка · обработано N» и обновляется
  сама (`<meta refresh 5s>`), по окончании — «последний прогон — …». HTTP-соединение больше
  не висит минутами.
- `web`: исключения обработчика ловятся (`do_GET`/`do_POST` → `_fail`): POST отвечает редиректом
  с текстом ошибки, GET — страницей «Не получилось выполнить запрос» (500); обрыв соединения
  клиентом (`BrokenPipe`) не пишется в трейсбек.

**Новое.** В карточке вакансии — кнопки «Сгенерировать письмо» и «Оценить вакансию»
(`POST /run/letters/<id>`, `POST /run/score/<id>`): работают только с этой вакансией. Правка
человека (`letters.edited=1`) не затирается — возвращается «письмо не изменено: сохранена ваша
правка»; при пустом письме подсказка меняется на «письма пока нет — нажмите …».
Добавлены `jobs.score_one` и `jobs.make_letter_for`.

**Убрано.** Кнопка «Воронка и ответы» из панели и ссылка «Воронка» из карточки. Страница
`/funnel`, `analytics` и данные остались (прямой адрес и CLI); если раздел не нужен совсем —
удалить `render_funnel`, маршрут `/funnel` и его тесты.

**Проверено:** `Ran 234 tests … OK` (+9: WAL/busy_timeout, одиночные оценка и письмо, правка
не затирается, «занято» вместо второго прогона, страница ошибки). Живой прогон `_smoke.py` на
временной базе — 34/34: главная, карточка, оценка/письмо одной вакансии, сохранение правки,
статусы, mark/skip, пакетные оценка и письма (фон), `/letter/<id>`, `/export`, `/queries`,
`/funnel`, статика, 404. Боевой сервер: `journal_mode=wal`, `POST /run/score` → «запущено:
оценка», через 8 с главная — «последний прогон — оценено новых: 0 (всего оценено: 74)»,
карточка `/v/138379175` содержит обе кнопки, «Воронки» нет, ошибок в журнале за 10 минут — 0,
md5 файлов совпадают с локальными.

**Следующий шаг:** заказчику нажать «Оценить» и «Сгенерировать письмо» в карточке; после клика
на главной сразу появляется плашка прогресса. Если «Воронка» не нужна и как страница —
сказать, удалю маршрут и `analytics`.

## 24.10.2026 — фон интерфейса: офис по новой фотографии заказчика

**Сделано:** заказчик прислал другое фото (офис: сотрудники за столом переговоров, белые
стены, мягкий боке) — фон заменён, панели стали плотнее, чтобы текст не «плавал» на светлом.

- `hhassist/static/bg.jpg` — 1600×1000, 110 КБ (было 252 КБ). Исходник 1024×1024 (`.jfif`):
  кадр обрезан по центру до пропорции 1.6 и дотянут до 1600×1000, затем `UnsharpMask` +
  насыщенность/контраст и мягкое затемнение верхней и нижней полос — тем же путём, что и

- CSS: `url('/static/bg.jpg?v=3')` — сброс кэша у тех, кто уже открывал интерфейс
  (`Cache-Control: max-age=604800` держит старую картинку неделю); сам файл по-прежнему
  отдаётся белым списком имён, query отбрасывается `urlparse`.
- Фото светлее прежнего, поэтому непрозрачность панелей поднята: таблица `.82 → .88`,

  читаются сквозь строки.
- Новый тест `test_background_url_is_versioned`: в CSS обязан быть `bg.jpg?v=N` — забытая
  версия означает старый фон в браузере заказчика ещё неделю.

**Проверено:** `Ran 225 tests … OK`; скриншоты 1920×1080 и 1280×900 (таблица, кнопки и
селекты читаются); боевой сервер — `bg.jpg?v=3` в HTML, `/static/bg.jpg` 109 789 байт,
md5 `a5e3f342…` совпадает с локальным, `web.py` на сервере совпадает по md5, сервис `active`.

**Следующий шаг:** заказчику обновить страницу (Ctrl+F5, если браузер держит картинку);
если исходник появится в большем разрешении — пересобрать с `--from` и поднять версию до `v=4`.

## 24.10.2026 — один выбор региона, ровные кнопки, доверенный сертификат на IP

**Сделано** по замечаниям заказчика: «выбор регионов — в одном месте, сейчас в двух»,
«выровняй кнопки на странице», «Яндекс не может открыть приложение».

- **Регион в одном месте.** Было два независимых селекта: «регион сбора» рядом с кнопкой
  «Собрать вакансии» (id области hh) и «регион» в фильтре списка (название из базы) — выбрать
  один и тот же регион дважды было невозможно. Теперь на главной один селект: значения —
  id субъекта hh (`113` — вся Россия, `2019` — Московская область), он же задаёт `area_ids`
  для сборщика и фильтр списка; `web._resolve_region` переводит id ↔ название и принимает
  старое значение-название, поэтому прежние закладки работают. Город остался отдельным
  фильтром (`name='city'`, раньше `area`), при смене региона он сбрасывается.
- **Кнопки.** Все действия — в одной панели `.toolbar`: первая строка — селекты, вторая —
  кнопки; `formaction`/`formmethod` на кнопках отправляют POST в `/run/*` без второй формы.
  `.btn` стал `inline-flex` с фиксированной высотой 36px (`<a>` и `<button>` больше не
  расходятся на 1–2 px), у `select` та же высота, `.actions form` — flex без отступов.
  Попутно `.card table{display:table;width:100%}`: таблицы внутри карточек больше не
  сжимаются по содержимому (на «Воронке» шапка обрезалась после третьей колонки).
- **Сертификат.** Яндекс.Браузер на самоподписанный сертификат показывает
  `ERR_CERT_AUTHORITY_INVALID` и **не даёт** ссылки «всё равно перейти» (в Chrome/Firefox она
  есть). Let's Encrypt с 2026 года выдаёт сертификаты на IP, но только с профилем
  `shortlived` (6 дней) и через certbot 5.4+; в Ubuntu 24.04 лежит certbot 2.9.0 без флагов
  `--ip-address`, snap на сервере не установлен. Решение: свежий certbot в отдельный venv
  `/opt/certbot-ip` (5.8.0), выпуск `certonly --preferred-profile shortlived --webroot
  -w /var/www/certbot --ip-address 135.106.183.205` (http-01 обслуживает уже работающий
  nginx), hook `/usr/local/bin/hh-tls-deploy.sh` кладёт `fullchain.pem`/`privkey.pem`
  в `config/tls.crt|key` и перезапускает сервис, systemd-таймер `hh-certbot-renew.timer`
  проверяет продление дважды в сутки (`certbot renew` для 6-дневного серта).
  Всё повторяемо: `deploy/letsencrypt-ip.sh` (параметры `--ip`, `--webroot`, `--dir`,
  `--user`, `--email`, `--dry-run`).
- **Проверено:** `Ran 224 tests … OK` (новый `tests/test_web_layout.py` — 16 тестов: один
  селект региона, фильтр по id, «вся Россия» без фильтра, город, панель `.toolbar`,
  единая высота в CSS, POST `/run/collect` с регионом из селекта); `openssl s_client` и
  `ssl` из Python — issuer `Let's Encrypt YE1`, SAN `IP Address:135.106.183.205`,
  `notAfter Oct 31 2026`, проверка системными корнями проходит; боевая страница —
  HTTP 200 (22 153 байта), `name='region'` = 1, `name='area'` = 0, `formaction` = 3.
  Скриншоты главной, карточки и воронки — кнопки и селекты одной высоты.

**Проблема:** `certbot renew --dry-run` отвечал «Another instance of Certbot is already
running» — блокировку держал прерванный прогон (ssh-сессия закрывалась по таймауту
терминала), после его завершения `fuser` показал, что lock свободен, и dry-run прошёл.

**Следующий шаг:** сертификат живёт 6 дней — проверить через сутки
`systemctl list-timers hh-certbot-renew.timer` и `openssl x509 -enddate` на боевом `tls.crt`;
при смене IP — `deploy/letsencrypt-ip.sh` заново.

## 24.10.2026 — деплой на VPS Selectel: https://135.106.183.205:8443

**Сделано:** ассистент поднят на арендованном VPS (Ubuntu 24.04, регион ru-7) рядом с уже
работающими matvey-bot, nightscout-monitor, nginx и Postfix. Адрес —
`https://135.106.183.205:8443` (самоподписанный сертификат на IP), вход по паролю
(логин `hh`); пароль сгенерировал установщик, он лежит только в `/opt/hh-assistant/.env`.

- код: `git clone` из GitHub → `/opt/hh-assistant`; systemd-юнит `hh-assistant`,
  пользователь `hhassist`, `ProtectSystem=strict` + `ReadWritePaths data/out/config`,
  `MemoryMax=600M`;
- статика: `hhassist/static/bg.jpg` отдаётся тем же сервером (200 `image/jpeg`,
  `Cache-Control` на неделю) — проверено снаружи;
- секреты перенесены по scp: `.env` (`LLM_PROVIDER`/`MODEL`/`API_KEY`/`BASE_URL`,
  `HH_USER_AGENT`, лимиты) и `config/profile.json`; серверные `WEB_*` не перезаписывались.

**Проблема 1 — установщик включал ufw «как есть».** На сервере ufw не было, а наружу смотрят
22, 25 (почта), 80 и 443 (nginx), 8080 (nightscout). `install.sh` делает `ufw --force enable`
только с правилами SSH и 8443 — это закрыло бы почту и сайт заказчика. Решение: ufw поставлен
и настроен **до** установки (правила для всех рабочих портов + «страховка»: сам выключился бы
через 10 минут, если доступ не подтверждён), затем запущен `install.sh` — он только добавил
свои правила.

**Проблема 2 — сервис поднялся по HTTP.** В `.env.example` уже есть пустые `WEB_TLS_CERT=` и
`WEB_TLS_KEY=`, а `install.sh` проверял лишь наличие ключа (`grep '^WEB_TLS_CERT='`), поэтому
пути к сертификату не записались и сервер стартовал как `http://0.0.0.0:8443` (curl → `000`,
в журнале предупреждение «пароль передаётся по HTTP»). Исправлено в `deploy/install.sh`:
функция `set_env` вписывает значение, если оно пустое (то же для `WEB_AUTH_USER`); шаг проверки
теперь различает `401/200` и «нет ответа» с подсказкой про `journalctl`.

**Проверено снаружи (не с сервера):** `https://135.106.183.205:8443/` → `401` без пароля,
`200` с паролем (20 753 байта, в HTML есть `/static/bg.jpg`); `/static/bg.jpg` → `200
image/jpeg`, 40 080 байт; внутри сервера `https://127.0.0.1:8443` тоже `200`; журнал:
`hh-assistant: https://0.0.0.0:8443`. Почта и сайт после включения ufw работают
(правила 25/80/443 на месте).

## 23.10.2026 (этап 7) — вход по паролю, HTTPS и размещение на сервере

**Сделано:** веб-интерфейс научился закрываться входом и работать по HTTPS, а в репозитории
появился `deploy/`: `install.sh` (Ubuntu/Debian), systemd-юнит `hh-assistant.service` и
`deploy/README.md` — пошаговое размещение на VPS Selectel с доступом по IP.

- `WEB_AUTH_USER` / `WEB_AUTH_PASSWORD` — HTTP Basic: браузер сам показывает окно входа.
  Проверка заголовка `Authorization` идёт через `hmac.compare_digest` (без утечки по времени),
  пароль в UTF-8, поэтому кириллица работает.
- Если пароль не задан, а запрос пришёл не с петлевого адреса, сервер отвечает `403` с
  подсказкой «задайте WEB_AUTH_USER/WEB_AUTH_PASSWORD». Это страховка от `--host 0.0.0.0`
  «на минутку»: данные профиля (телефон, почта) и кнопки сбора/писем наружу не уходят.
- `WEB_TLS_CERT` + `WEB_TLS_KEY` — сервер поднимает HTTPS (`ssl.SSLContext`,
  `wrap_socket`), в консоль печатается `https://…`; при заданном пароле без TLS выводится
  предупреждение, что пароль идёт открытым текстом.

**Почему так:** запрос был «разместить на Selectel с входом по IP». Публичный IP без пароля
означает, что любой желающий может запустить сбор вакансий, генерацию писем (траты на LLM) и
прочитать персональные данные из `config/profile.json`. Домен и Let's Encrypt для IP не
выдаются, поэтому выбран самоподписанный сертификат: браузер предупреждает один раз, зато
пароль не идёт по сети в открытом виде. Вход сделан именно Basic, а не формой с сессией:
приложение на stdlib, а одна пара логин/пароль для одного человека не требует хранилища сессий.

**Проверено:** `python -m unittest discover -s tests` — **203 теста**, OK (+19 в
`tests/test_web_auth.py`: разбор `Basic` с кириллицей и двоеточием в пароле, битый base64,
петлевые адреса, правила «пароль задан/не задан», `_authorized` без сокета, `WWW-Authenticate`
только на `401`). Живой прогон (`0.0.0.0:8799`, временная копия приложения с `.env`):
без пароля `401` + `WWW-Authenticate: Basic realm="hh-assistant"`, с верным паролем `200`

**Опубликовано:** коммит `9a9a459` и `git push origin main` (`67b95db..9a9a459`) — установка

## 23.10.2026 — этап 6 «Доработки по итогам работы»

**Сделано:** пять улучшений по замечаниям после первых прогонов.

1. **Письмо правится руками.** В карточке текст письма теперь внутри формы: `POST /letter/<id>`
   сохраняет отредактированный текст, `letters.edited=1` помечает правку, и генерация
   (`jobs.make_letters`, в том числе с `--force`) такие письма больше не перезаписывает.
   В CLI появилась команда `letter <id> [--file путь]` (показать/заменить).
   Почему так, а не «история версий»: для одного письма хватает флага «правил человек»,
   отдельная таблица версий — лишняя сущность без сценария использования.
2. **Одна компания — один отклик за 10 дней.** `queue.cooldown_companies()` собирает компании,
   куда откликались за `COMPANY_COOLDOWN_DAYS` (10) дней, `next_batch()` и `jobs.letter_vacancies()`
   их отсеивают (выборка с запасом `limit*3`, чтобы после фильтрации пачка осталась полной).
   Раньше в одну компанию могло уходить по 3–4 отклика подряд.
3. **Инкрементальный сбор.** `collector.collect(known=..., refresh_days=...)`: id, которые видели
   меньше `COLLECT_REFRESH_DAYS` (3) дней назад, повторно не скачиваются; в отчёте видно
   «новых / обновлено / уже в базе». Для этого у вакансий появилась колонка `seen_at`.
4. **Health-check парсера.** `collector.quality()` даёт `ok | suspect | empty | no_results`:
   `suspect` — если у большинства вакансий пустой заголовок или описание короче 100 символов
   (порог — минимум 3 совпадения и больше половины пачки, чтобы одиночные результаты не пугали).
   При `suspect/empty` пишется событие `parser_suspect`, на главной сутки висит баннер.
5. **Регионы.** `COLLECT_AREAS` (по умолчанию `113` — вся Россия) — id через запятую или имена
   (`moscow`, `spb`, `rf`); `area` уходит в поиск повторяющимся параметром
   (`urlencode(..., doseq=True)`), для API и HTML одинаково. Регион вакансии парсится
   (`area`, `area_id`: JSON-блок у API/HTML), хранится в `vacancies` и показывается фильтром
   на главной (список городов берётся из самой базы — без отдельного справочника регионов).
   Плюс `COLLECT_REMOTE`/`--remote` — только удалёнка.

**Проблема:** старые базы не имеют новых колонок, а система миграций в проекте отсутствовала.
**Как решено:** `storage._migrate()` — аддитивные `ALTER TABLE` по `PRAGMA table_info`,
с бэкфиллом `seen_at = created_at`; пишет только когда колонки действительно не хватает
(иначе каждый `connect()` открывал бы транзакцию и мешал соседним соединениям — поймано тестом
на «upsert без commit»).

**Тесты:** `tests/test_improvements.py` — 26 новых (миграции, правка письма, кулдаун, инкремент,
health-check, регионы), всего **169**, все зелёные.

**Следующий шаг:** собрать базу с `COLLECT_AREAS=113`, оценить, отфильтровать по городу,
проверить, что кулдаун не режет полезные вакансии при `COMPANY_COOLDOWN_DAYS=10`.

### Правки по замечаниям пользователя (тот же день)

**Замечания:** «выбор региона не работает», «при запуске .bat открывается два терминала»,
«всё равно собирается 9 вакансий всего».

**Что выяснилось живыми проверками (не догадками):**
- hh отдаёт город и субъект РФ в JSON-LD `JobPosting` (`addressLocality` / `addressRegion`),
  а старые `data-qa="vacancy-view-location"` и `"area": {"id", "name"}` из разметки исчезли —
  поэтому `area_id` в базе был пустым у всех вакансий;
- фильтр по городу применялся **после** отсечения по порогу и лимиту (`next_batch(threshold, limit)`
  → фильтр в Python), поэтому при пороге 55 из 147 вакансий проходили 9, и почти любой город
  давал пустую страницу;
- список регионов строился из городов в базе: «деревня Вырубово», «посёлок Усть-Луга» —
  субъектов РФ там не было;
- «9 вакансий» — это не сбор, а **очередь**: `collect --limit 20` по 5 запросам сохранял новые
  пачки, но на главной показывались только 9 вакансий с баллом ≥ 55, а порог в интерфейсе
  был скрытым полем (`/?threshold=…`), сводки не было;
- `.bat` были записаны с LF-переводами строк: cmd склеивал команды (`>nulstart`, `utf-8if`,
  `базы.cd`) — часть шагов молча не выполнялась, а `start "" /min cmd /c` открывал второе окно.

**Что сделано:**
1. `hhassist/areas.py` — справочник 89 субъектов РФ с `api.hh.ru/areas/113`, кэш `data/areas.json`
   на 30 дней, встроенный фолбэк на 10 регионов без сети; `cached()` не ходит в сеть никогда,
   `ensure()` — по TTL. Команда `python cli.py areas [--refresh]`.
2. Колонка `vacancies.region`; парсер берёт город и субъект из JSON-LD (старые варианты оставлены
   фолбэками); `api_adapter` читает `address.region`.
3. Фильтры в SQL: `queue.next_batch(..., region, area)`; для строк без `region` сравнение идёт
   по городу, чтобы старые вакансии не выпадали. На главной — регион → город → порог (55/40/0)
   и сводка «собрано в базе · оценено · выше порога · ниже порога · без оценки · в списке».
4. Регион сбора выбирается прямо в браузере: `POST /run/collect` с `area=<id>`, в отчёте
   печатается регион.
5. `.bat` перезаписаны с CRLF и без BOM: сервер работает в том же окне (`python … serve`),
   браузер открывается фоновым `start "" /b cmd /c "ping … & start http://…"`.

**Проверено:** `Ran 177 tests … OK`; живой сбор `collect --areas 1 --limit 3` записал 3 вакансии
с `region='Москва'`; `render_index` на боевой базе: порог 0 → 50 строк, порог 55 → 9, фильтр
